# Windows 11 desktop menu prototype

Goal: a desktop-background command in the Windows 11 first-level menu, enabled explicitly from MyFences settings. Registration success alone does not prove visibility on the real desktop.

## Sources and route

Microsoft documents native IExplorerCommand, a surrogate COM server, and sparse identity for unpackaged apps: https://learn.microsoft.com/en-us/windows/apps/desktop/modernize/integrate-packaged-app-with-file-explorer

The documented modern background type is Directory\Background. DesktopBackground is documented for classic verbs, but the modern schema does not explicitly document a desktop-specific equivalent: https://learn.microsoft.com/en-us/windows/win32/shell/reg-shell-exts

Signing and per-user registration: https://learn.microsoft.com/en-us/windows/apps/desktop/modernize/grant-identity-to-nonpackaged-apps

Signed packages differ from unsigned loose-layout registration requiring Developer Mode: https://learn.microsoft.com/en-us/windows/apps/dev-tools/winapp-cli/security

## Observations — 2026-10-04

No native compiler or Windows SDK was installed. Portable llvm-mingw 20260922 and Microsoft.Windows.SDK.BuildTools 10.0.28000.2705 were acquired in ignored .local/desktop-menu-tools. No installer or Developer Mode setting changed.

Run scripts/build-desktop-menu.ps1 -OutputDirectory .local/desktop-menu-prototype -Prototype. The script builds an x64 DLL and real PNG assets, packs the manifest, and signs an identity MSIX using a private key outside the distributable directory. A prototype-mode marker makes Invoke write only prototype.log; it does not alter grouping.

Compilation succeeded without warnings. Export inspection found DllGetClassObject and DllCanUnloadNow; imports are Windows DLLs/UCRT API sets. SDK schema validation, packing and signing passed. Prototype GetState stays enabled to avoid app-filtering false negatives.

Import into CurrentUser\TrustedPeople succeeded. Add-AppxPackage nevertheless failed with HRESULT 0x80073CF0 and nested 0x800B0109: the package root signature certificate must be trusted. This is an installation failure, not evidence that a desktop first-level command cannot work. Machine-wide trust has not been changed at this checkpoint.

The user subsequently authorized only certificate thumbprint 8AE76C2ED6EBC8272F649836B75AB21F7BA0F555 in LocalMachine\TrustedPeople. A normal escalated sandbox process still returned AccessDenied, so a fixed fingerprint-checking script was launched using RunAs. The user manually handled Windows UAC. Its result file and a read-only certificate-store lookup confirmed the same thumbprint. No Developer Mode setting changed.

The signed identity package then installed successfully as MyFences.DesktopMenu 0.2.0.0, Status Ok, IsDevelopmentMode False. Independent native CoCreateInstance of IExplorerCommand and GetTitle returned S_OK. Those checks diagnose activation only.

The user confirmed seeing and clicking the prototype in the first-level context menu on the real desktop. The prototype log contains state-desktop, title and invoke. This confirms Directory\Background reaches the desktop on the tested system, and IObjectWithSite / SID_SFolderView / IPersistFolder2 empty-PIDL identifies the desktop. Prototype invocation did not modify grouping.

The first-level route is selected for delivery. The identity package remains unregistered until settings explicitly enables it. Personal builds need the public certificate trusted in LocalMachine\TrustedPeople using the separately invoked administrator script; enabling the menu does not silently install trust. Moving the EXE requires Enable / update location, which removes only MyFences.DesktopMenu and re-registers it with the new external location. Disable retains layout and the separately trusted certificate.

The main agent verified first registration, same-version path update, removal and re-enabling against the built portable folder. Effective external paths were read using GetPackagePathByFullName2, PackagePathType_EffectiveExternal, through api-ms-win-appmodel-runtime-l1-1-3.dll. Get-AppxPackage has no ExternalLocation property on the tested machine.

Direct new-group IPC reached the real candidate, but the naming dialog remained behind foreground applications. Explicit activation exposed it and confirmation saved the isolated group. The second launcher now grants the named-pipe server foreground permission before dispatch.

An end-to-end registered COM Invoke probe reproduced 0x80070002. Diagnostic reads from the packaged surrogate returned ERROR_FILE_NOT_FOUND for both Title and ExecutablePath in the unpackaged app's HKCU key, although the host shell could read that key. The native command now derives MyFences.exe from ModuleDirectory and reads a UTF-16 caption file generated by Enable. The same registered probe then returned S_OK. Computer Use confirmed cancellation without saved changes, successful naming and live desktop visibility, normal Settings path updates, and --new-group startup without the initial Settings window. The probe source is activation-probe.cpp; --invoke only opens a dialog and does not emulate a user's real Explorer foreground gesture.
